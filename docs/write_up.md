Authorization Document Reader
Eljon G. Mateo | AI Automation Specialist mateoeljon@gmail.com | eljonmateo.dev
What I Built
A fully automated data extraction pipeline that ingests authorization PDFs from school districts and writes structured data directly into a Google Sheet masterfile , eliminating manual data entry entirely.
The system works in two paths. Text-based PDFs are extracted directly and sent to Claude Haiku via OpenRouter for fast, structured data extraction. Scanned or image-based PDFs are detected automatically when the cleaned text length falls below 50 characters, the file is then redownloaded and sent to the Anthropic API using the dedicated PDF document type for vision-based extraction. Both paths feed into the same validation and Google Sheet update logic.
Before writing to the sheet the system validates every field, detects which authorization date column to populate (1st through 4th) based on what's already filled, appends new comments to existing ones rather than overwriting, formats case manager names from Last, First to First Last, and logs any missing fields or issues to a dedicated Warnings sheet, without crashing or blocking subsequent documents.
2–3 Tradeoffs I Considered
1. Native Anthropic Node vs Direct HTTP Request for vision I initially attempted to handle the scanned PDF fallback through n8n's native nodes. The problem was that binary data doesn't survive cleanly through routing nodes like the IF node, n8n passes a filesystem reference rather than the actual binary. I considered using a Merge node to combine the routing decision with the binary data, but ultimately the cleanest solution was redownloading the file fresh on the FALSE path. This adds one extra API call per scanned document but eliminates an entire class of binary handling errors that would have been difficult to debug in production.
2. Single extraction path vs dual path Using Claude's vision API for every document regardless of type would have simplified the workflow significantly, one path, one node, no routing logic. I chose the dual path approach because text extraction is meaningfully faster and cheaper for clean PDFs, and the vision API should only be invoked when genuinely needed. For a system that will process hundreds of documents over time the cost difference is significant. The tradeoff is added workflow complexity and the whitespace cleaning logic needed to correctly detect scanned documents.
3. Google Sheets Lookup node vs reading all rows n8n's native Sheets Lookup node has limitations with partial matches and case sensitivity. I chose to read all rows and perform the student matching in a Code node using case-insensitive comparison instead. This is less efficient for large sheets, it reads every row on every trigger but gives full control over matching logic and handles edge cases like inconsistent capitalization in student names. For the current dataset size this is not a performance concern.
What I'd Improve With Another 10 Hours
1. Smarter authorization column detection The current system writes to the first empty authorization date column sequentially. With more time I'd extract the authorization number from the new document and cross-check it against existing authorization comments to detect whether this is a truly new authorization or an update to an existing one, preventing duplicate entries when the same authorization is uploaded more than once.
2. Email trigger instead of Google Drive upload, the current trigger requires someone to manually upload the PDF to the Drive folder. The training guide describes coordinators sending authorization details via email. With another 10 hours I'd add a Gmail trigger that monitors a designated inbox, extracts PDF attachments automatically, and processes them without any manual upload step, removing the last human touchpoint in the pipeline.
3. Confidence scoring on extracted fields The current system flags fields as missing when they return null but doesn't flag fields where the LLM extracted a value it may not be confident about. I'd add a second Claude call that reviews the extracted JSON against the original document text and rates confidence per field, flagging low-confidence extractions for human review even when a value was found.
Edge Cases I Noticed in the Data
1. Whitespace-only PDF extraction The sample scanned PDF produced extraction output containing only newline characters, which technically exists as a string but carries no real content. A naive text exists check would have incorrectly routed this to the text extraction path. I added a whitespace stripping step before the length check to handle this correctly.
2. Authorization comments are cumulative not replaceable Looking at the existing sheet data particularly Aaron Mitchell's record, authorization comments span multiple authorization periods and contain detailed history going back years. Overwriting this field would destroy critical history. I changed the logic to append new comments to existing ones rather than replace them, preserving the full audit trail.
3. Multiple authorization periods per student, the sheet has four separate authorization date columns, 1st through 4th Auth. A system that blindly writes to the first column would overwrite existing records. I built logic to detect which columns are already populated and write to the next available one, with a warning logged if all four are full.
4. Case manager name format inconsistency The sample PDF listed the caseworker as SMITH, JORDAN in Last, First format while the sheet stores names as First Last. I added formatting logic to detect and convert the comma-separated format automatically, ensuring consistency with existing records.
5. Student not found in masterfile, the system handles the case where an authorization arrives for a student who doesn't yet exist in the sheet by appending a new row rather than failing silently, ensuring no authorization is ever dropped regardless of whether the student record exists.
